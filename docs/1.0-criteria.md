# The 1.0 bar

Status: written bar, not aspiration. This document records what a 1.0 release
must be able to demonstrate, the evidence for each criterion as of commit
`c4c17e5` on `main`, and what is still open. A criterion is **Met** only when
the evidence is reproducible from this repository; a claim that cannot be
checked here is **Open**, even when it is probably true.

The package version is `0.7.0`. Nothing in this document cuts a release
or changes behaviour; it is the acceptance test for one.

## 1. Published JSON Schemas, enforced in CI

**Met.** The contract is published as data, not as prose:

- `src/tackboard/schemas/` (also reachable as the repository-root `schemas`
  symlink) holds **26 JSON Schema files**: 25 document shapes plus
  `task.json`, the shared task projection that the others reference by URN.
  The 25 document names are enumerated in
  `scripts/validate_schemas.py::EXPECTED_DOCUMENTS`; `task.json` is a
  definitions document and is not produced as a standalone CLI document.
- Every schema sets `additionalProperties: false` and carries the document's
  `schema_version` as a constant. An additive field therefore cannot be emitted
  until its schema is updated.
- `scripts/validate_schemas.py` runs the CLI against a scratch board — and a
  real `tack serve` process for the HTTP documents — and validates each produced
  document against its schema. It validated **29 document instances with 0
  failures** in this working tree (`board` is produced twice, with and without
  `tasks`; `api_task` twice, for a claimed and an unclaimed task); it also
  checks that `tack schema --json` lists exactly the packaged set.
- `.github/workflows/ci.yml` runs that script twice in the `test` job: once
  in process (`uv run python scripts/validate_schemas.py --tack "uv run tack"`)
  and once through the installed console script. The same workflow's `build`
  job checks that the wheel and sdist each ship at least 26 schema files. The
  validation was added in commit `c302bdc` ("ci: validate every JSON document
  against its published schema"); the current job definition is at `c4c17e5`.

The set also covers the **HTTP** documents. The read-only web view publishes
four JSON documents, and they are held to the same obligation by
`docs/api-contract.md`: each is a superset of its CLI counterpart, and its
additions are declared in a schema. `/api/board` and `/api/memo` validate
against `board.json` and `memo.json` unchanged; `/api/graph` validates against
`api_graph.json` (the CLI node plus the four derived readiness flags) and
`/api/tasks/<id>` against `api_task.json` (the `tack show` document plus the
claim, prerequisites, dependents and the capped history). An undeclared key on
either route therefore fails validation exactly as an undeclared CLI key does.
Publishing them moved the count from 24 files (23 document shapes) to **26
files**: 25 document shapes plus the shared task projection.

"Published" here means committed to the repository and shipped inside the
package. The `$id`s are URNs; no hosted URL is implied or served. A consumer
builds a resolver from the documents listed by `tack schema --json`.

The one thing this does not prove from this machine is that the GitHub-hosted
`test` job is currently green. The workflow definition enforces the check; the
hosted run itself is outside what can be observed here. The local run above is
the evidence available in this tree.

## 2. Deprecation policy

This policy applies from 1.0 onward. It covers the four public surfaces: CLI
flags, exit codes, JSON fields and database schema versions. Human output and
diagnostic message wording are explicitly outside it — they may be reworded in
any release.

### 2.1 The three version numbers are independent

| Surface | Current value | Changes when |
|---|---|---|
| Package release | `0.6.0` | Any release |
| JSON document `schema_version` | `1` | A breaking change to a document shape |
| Database `PRAGMA user_version` | `2` | A DDL change that needs a migration |

A release may bump one without the others. Do not infer a database migration
from a package minor, or a document break from a database bump.

### 2.2 What may change in a 0.x minor

While the project is 0.x, a minor release may:

- add a command, an option, an exit-code case or a JSON field;
- change behaviour and document it in `CHANGELOG.md`;
- deprecate a flag, field or command, provided it still works in that release;
- add a database schema version with a migration from every released version.

It may not remove or rename a JSON field, change a field's type or meaning,
reuse or change the meaning of an exit code, or remove a flag without the
deprecation step below. Those are breaking changes and wait for a major release
once 1.0 is cut. The 0.x line has one precedent for a deliberate breaking
behaviour change: 0.2.0 made a claim stop writing the assignment. It kept the
document shape additive and documented the new refusal, so no `schema_version`
bump was needed.

### 2.3 What requires a new `schema_version`

A new JSON document `schema_version` is required for any change that a strict
consumer validating against the published schema would reject:

- removing or renaming a field or document;
- changing a field's type, nullability or meaning;
- changing the error envelope's shape or an exit-code mapping;
- changing the meaning of an existing enum value.

Adding a field does **not** require a bump: `schema_version` stays `1`, the
schema is updated with `additionalProperties: false` satisfied, and the change
is listed as additive in `CHANGELOG.md`. A breaking change ships as a new
`schema_version`, with the old document still available for at least one
released minor; the CLI selects the version, never the consumer guessing.

### 2.4 How long a deprecated flag lives

- **0.x:** at least one full released minor. A flag deprecated in 0.5.0 may be
  removed no earlier than 0.6.0, and never in the same release that deprecates
  it.
- **1.x:** for the whole 1.x line. A deprecation announced in any 1.x release
  is not removed before 2.0. This is the cost of a stable contract, and it is
  deliberate.

A deprecated flag keeps its documented behaviour for the whole window. It is
not silently ignored and it does not become a no-op. Its help text and the
reference topic name the replacement and the release that will remove it.

### 2.5 What a removal needs

A removal is a breaking change. It needs all of the following in one change:

1. A `CHANGELOG.md` entry in the release that deprecates it, naming the
   replacement and the first release in which removal is allowed.
2. The reference text (`README.md`, `SKILL.md` topic, `tack guide`) updated to
   stop teaching the old form and to name the new one.
3. A test that pins the old form's behaviour until removal, and a test that the
   replacement works.
4. For a JSON field: a new `schema_version`, a published schema for the old
   document for the deprecation window in 2.4, and a note in the document's
   schema description.
5. For a CLI flag: a usage error (exit 2) after removal that names the
   replacement — never a silent accept-and-ignore.
6. For a database schema version: a migration function from every prior
   version, a pre-migrate backup, a builder path in
   `scripts/build_legacy_board.py`, and a migration-matrix row.
7. A line in `docs/1.0-criteria.md` or its successor recording that the
   removal was made, so the bar's own history stays honest.

### 2.6 Exit codes

Exit codes are a closed, stable set: `0` success (including idempotent no-ops
and an empty `next`), `1` internal, `2` usage or missing actor, `3` not found
or not configured, `4` validation, invalid transition or cycle, `5`
concurrency conflict, `6` database, schema or migration problem. A code is
never removed or reused for a different meaning. A new code may be added only
when no existing code fits and the change is documented as additive. The
mapping stays mechanical: every exception in `errors.py` carries `code`,
`exit_code` and `retryable`, and the CLI renders whichever one arrives.

### 2.7 Database schema versions

- A DDL change bumps `PRAGMA user_version`. The bump ships with a migration
  function, a backup written before the migration, and a migration test from
  every released version (criterion 3).
- A board at an older version is refused with exit 6 until `tack migrate`
  runs; a board at a newer version is refused with exit 6 and tells the user to
  upgrade the package. Nothing auto-migrates.
- A migration must be transactional. If a backup cannot be written, the
  migration aborts without touching the database.
- `application_id` identifies the file family and does not change with the
  schema version.

## 3. Migration from every released schema version

**Met.** Two database schema versions have ever been released:

| Schema version | Released in |
|---|---|
| 1 | `v0.1.0` through `v0.2.0` |
| 2 | `v0.3.0` through `v0.6.0` |

The `migration` job in `.github/workflows/ci.yml` runs a matrix over
`[1, 2]`. For each version it builds a board with
`scripts/build_legacy_board.py --version N`, runs `tack migrate`, and requires
a clean `tack doctor` report (`scripts/check_doctor_clean.py`). The matrix was
added in commit `942a4b7` ("ci: migrate every released schema version and
doctor the result"). The version 1 fixture removes the memo table and its
triggers, so the 1 → 2 migration genuinely runs.

**Policy for version N+1.** When `SCHEMA_VERSION` becomes N+1:

1. Add the migration function from N to N+1; it must run in one transaction.
2. Extend `scripts/build_legacy_board.py` so it can build a board at N+1's
   predecessor state as well as every earlier version. The builder is how the
   matrix produces a real old board; a fixture copied from a newer board is not
   a substitute.
3. Extend the matrix to `[1, 2, ..., N+1]`. A row for a version that was ever
   released is never dropped, even when direct migration from it is no longer
   the common path.
4. Require `doctor` to be clean after every migration, and keep the pre-migrate
   backup assertion in the test suite.

The matrix tests released versions, not development snapshots. An unreleased
`schema_version` on `main` is covered by the suite's migration tests, not by a
matrix row, until a release tag exists for it.

## 4. Linux/macOS/Windows CI green, with a published scale benchmark

**Open.** Two halves, one met and one not:

- **Published scale benchmark: met.** `scripts/benchmark_scale.py` builds
  deterministic 1,000- and 10,000-task boards, has 50 distinct agents claim
  through `next --claim`, and reports p50/p95 for `next --claim`,
  `board --brief` and `graph --json`. The numbers are published in `README.md`
  ("Scale benchmark") and `DESIGN.md` §6 ("Measured contention ceiling"). The
  benchmark is tracked but ungated: no timing threshold fails CI. That is a
  deliberate policy, not an omission.
- **Three operating systems green: not met.** `ci.yml` defines only
  `ubuntu-latest`. macOS and Windows are absent. Whether the current Linux job
  is green on GitHub-hosted runners cannot be observed from this machine; the
  workflow definition and the local suite are the evidence available here.

The OS matrix was **not** added. It is not genuinely declarative against the
current workflow:

- The workflow's `run` steps use POSIX shell constructs (`$(...)`,
  `set -euo pipefail`, `/tmp/...`) and POSIX tools (`unzip`, `tar`, `rg`). The
  default Windows runner shell is PowerShell, so every `run` step would change
  execution environment.
- The installed-console-script validation invokes
  `$(uv tool dir --bin)/tack`; on Windows the executable is `tack.exe`, so that
  expression is wrong there.
- The repository-root `schemas` entry is a git symlink. A Windows checkout
  without symlink support materialises it as a plain file or fails; the package
  copy at `src/tackboard/schemas` still works, but a workflow step that reads
  the root path would not.
- SQLite's WAL locking and file-replacement semantics differ on Windows and on
  network filesystems. The suite exercises real multi-process concurrency and
  backup snapshots; those tests are the most likely to surface a platform
  difference.
- The migration and build jobs depend on `/tmp`, `unzip`, `tar` and `rg`, and
  are better kept on Linux for now.

Because those are real edits to existing steps, adding the matrix blind would
violate the "existing steps work unchanged" condition. The exact proposed diff
is below; it is a proposal only and is not applied.

```diff
--- a/.github/workflows/ci.yml
+++ b/.github/workflows/ci.yml
@@ -8,10 +8,14 @@ jobs:
   test:
-    runs-on: ubuntu-latest
+    runs-on: ${{ matrix.os }}
     strategy:
       fail-fast: false
       matrix:
+        os: [ubuntu-latest, macos-latest, windows-latest]
         python-version: ["3.12"]
+    defaults:
+      run:
+        shell: bash
     steps:
@@ -42,7 +46,11 @@ jobs:
       - name: JSON Schemas match real CLI output (installed console script)
-        run: uv run python scripts/validate_schemas.py --tack "$(uv tool dir --bin)/tack"
+        run: |
+          bin="$(uv tool dir --bin)"
+          exe="tack"
+          [ "${RUNNER_OS}" = "Windows" ] && exe="tack.exe"
+          uv run python scripts/validate_schemas.py --tack "${bin}/${exe}"
```

The proposed change leaves the `migration` and `build` jobs on `ubuntu-latest`.
It should be landed as its own change with its own CI run, not folded into a
documentation change. Platform-specific risks to watch on the first run:
path separators and drive letters in test fixtures; the symlink above; SQLite
WAL cleanup and file replacement on Windows; git worktree behaviour in the
`worktree-per-claim` example; and case-insensitive filesystems in tests that
assume distinct paths differing only by case. Until a run is observed and
green on all three runners, this criterion stays open.

## 5. `DESIGN.md` §10 non-goals reconciled

**Met by this change.** The deliberately-kept-out list itself is unchanged: no
accounts or authorization, no cross-project dependencies, no automatic lease
expiry or heartbeats, no bulk import, no web mutations, no automatic status
change on a dependency change, and no task deletion. The audit checked each
shipped surface against that list and found no contradiction. It did find
wording that had become ambiguous, and corrected it:

- **Stale claims are not a lease-expiry feature.** The projection's
  `claim_age_seconds`/`claim_stale`, `claims --stale` and `doctor`'s
  `stale_claim` warning make staleness visible; nothing expires a claim
  automatically. `recover` is a manual, audited `release --force` wrapper. The
  non-goal text now says so instead of leaving a reader to infer that no
  staleness concept exists.
- **The web view is read-only in the strict sense.** It accepts `GET` and
  `HEAD` only and exposes no write endpoint. `--allow-remote` changes the bind
  policy, not the mutation policy. The text now says that.
- **Advisory identifiers are not authorization.** The non-goal list already
  called agent IDs advisory; it now links the security note, so "no
  authorization" is not read as "the board is safe to expose".
- **Plan import, the memo and typed refs are already named in §10.** The audit
  confirmed that `plan apply` is create-only and cannot adopt an existing task,
  that the memo is not a task and nothing in `tasks`, `claims` or
  `dependencies` reads it, and that a typed `task:` ref points at an existing
  task without writing history. No text change was needed for those three.
- **`reject` and the schemas do not create an exception.** `reject` is the
  existing `review → in_progress` transition with a mandatory reason and the
  existing claim guard; the schemas describe documents and add no storage or
  command. Neither changes the list.

`docs/security.md` is the expanded statement of the security model the list
implies.

## 6. A recipe verified end to end in CI

**Met.** `examples/` contains three runnable recipes: `worktree-per-claim`,
`supervisor-loop`, and `planner-workers-reviewer`. `tests/test_examples.py`
executes all three as subprocesses against a fresh temporary board and asserts
both exit status and named output. The suite's `Test` step in `ci.yml` runs
those tests, so the recipes execute on every CI run; there is no separate
examples job.

**The CI end-to-end recipe is `planner-workers-reviewer`.** It is the one that
walks the whole board lifecycle in one run: `plan apply` creates a three-task
DAG; a worker claims a task and sends it to review; the reviewer rejects it
with a reason; the worker re-claims it and resubmits; the reviewer accepts it
and completes the rest; the run ends with all three tasks `done`. That
exercises plan application, the claim path, the `review → in_progress`
rejection path, re-claiming and completion — the largest slice of the contract
any single recipe covers.

**What "verified" means for it:** the test starts the recipe as a subprocess
with its own temporary database and no network, requires exit 0, and asserts
the specific lines `planner applied 3 tasks`, `reviewer rejected`,
`worker re-claimed`, and a final `'done': 3` count. A change that breaks any of
those paths fails the test rather than failing in a reader's terminal. The
other two recipes are verified the same way: `worktree-per-claim` also asserts
the `claim_conflict` refusal path, and `supervisor-loop` asserts bounded passes
and a persisted cursor.

This is test-level end-to-end verification inside CI, not a published demo
deployment. It proves the recipes run against the current CLI; it does not
prove they run against a packaged wheel on another OS.

## 7. Security note

**Met by this change.** `docs/security.md` covers the four required topics and
is linked from `README.md` and `DESIGN.md`:

- advisory agent IDs: labels, not authentication or authorization;
- the unauthenticated loopback web view: `GET`/`HEAD` only, `Host` validation,
  no remote bind without `--allow-remote` and an explicit `--allowed-host`;
- untrusted text: escaped on HTML output, JSON-encoded in documents, never
  executed, and the in-house Markdown renderer builds DOM nodes with
  `textContent` and accepts http(s) links only;
- the network-filesystem warning: `doctor`'s `network_filesystem` warning and
  the WAL-locking reason behind it.

The note also states the threat model plainly: the board prevents accidents,
not malice. See the document for the exact claims and the code that enforces
them.

## What 1.0 still needs

The only criterion not met is the operating-system matrix. Completing it needs
a separate change: land the proposed `ci.yml` diff (or an equivalent), run it
on GitHub-hosted runners, fix the platform-specific failures it exposes, and
publish the first green run for Linux, macOS and Windows. The benchmark should
then be re-run on at least one machine per platform, or the document should say
plainly that one canonical machine's numbers are the published ones. Everything
else in this bar is evidenced above.
